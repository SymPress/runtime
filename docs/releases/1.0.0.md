# Runtime 1.0.0

Runtime 1.0 establishes the [1.x compatibility contract](../compatibility-policy.md)
and stable installation from [Packagist](https://packagist.org/packages/sympress/runtime).
It requires PHP `^8.5`, Composer 2.10.3 or newer within 2.x, and Symfony `^8.1`.
The SymPress kernel is optional. See the [platform table](../platforms.md) for the
operating-system scope and Windows durability limits.

## What becomes stable

- The documented [PHP extension API](../api.md), including public service methods.
- Existing configuration keys/defaults, commands/options, exit meanings,
  environment controls, WordPress hooks and managed configuration sections.
- The supported [download-lock, cache, dump and payload formats](../file-formats.md).

A breaking change to a supported interface requires a new major release.
Deprecations are announced at least one minor release before removal and removed
only in the next major. Legacy compatibility adapters remain supported throughout
1.x and are scheduled for removal in 2.0. Implementation details marked `@internal`
are outside the public API promise.

## Install from Packagist

For a new WordPress site, use the complete [getting-started guide](../getting-started.md).
To install only the package in an empty project:

```sh
mkdir runtime-check
cd runtime-check
composer init --name=example/runtime-check --no-interaction
composer config allow-plugins.sympress/runtime true
composer require 'sympress/runtime:^1.0'
vendor/bin/runtime --version
```

No Runtime-specific repository or credentials are needed. An unconfigured project
without WordPress Core receives the executable but defers automatic setup. This
does not install a working WordPress site. Commit `composer.lock` to retain the
resolved package versions; `^1.0` permits compatible stable 1.x updates.

## Upgrade from 0.x or a prerelease

For 0.1, first follow the [0.2 upgrade guide](0.2.0.md), including the executable
rename to `runtime`. For 0.2 or a 1.0 prerelease:

1. Keep the working Composer/download locks, generated configuration, private
   environment artifacts and their matching `var/runtime` payloads available for
   rollback. Work in an isolated build or branch.
2. Remove only the Runtime-specific VCS repository if one remains. Preserve
   WPackagist and repositories needed by other dependencies. Allow the Runtime
   Composer plugin explicitly, then update the requirement without running setup:

   ```sh
   composer config allow-plugins.sympress/runtime true
   composer require 'sympress/runtime:^1.0' --no-plugins --no-scripts
   ```

3. Review the Composer lock and custom extensions against the public API. Keep
   existing site URLs, web-server routes and retained PHP sections unchanged.
   Install the reviewed lock and validate the generated result:

   ```sh
   composer install --no-interaction
   vendor/bin/runtime validate
   vendor/bin/runtime --no-interaction
   vendor/bin/runtime doctor
   ```

4. Review and commit intended manifest/lock changes, including any reviewed
   `sympress-runtime.lock` changes. Check homepage, login, admin, scheduled work
   and custom steps. Run `doctor --production` as the deployment PHP identity
   for production builds; use the [deployment guide](../deployment.md) to handle
   environment dumps, retained payloads and read-only operation.

Native WP-CLI configuration registers `wp runtime` before WordPress loads.
Existing user-owned YAML and legacy profiles are preserved; review or add the
[registration entry point](../wp-cli.md) before using it. Composer supports
`composer runtime` and colon-form diagnostic aliases such as
`composer runtime:doctor --json`.

Version-only 0.2 download locks remain readable. A changed lock write adds
`format: 1` while retaining `version: 1`; existing pins are preserved. Unknown
future formats are rejected or preserved rather than silently overwritten.
Do not delete an old payload that is still referenced by a rollback configuration.
When changing environment or compatibility mode, flush the runtime cache and
explicitly rebuild deployment dumps.

## Existing compatibility configurations

Use the dedicated [migration guide](../compatibility.md) to preview configuration
and PHP changes before replacing the previous setup. The
[parity matrix](https://github.com/SymPress/runtime/blob/main/docs/maintainers/parity.md) records the compatibility comparison;
profile-specific differences are documented rather than hidden by a rename.
A successful migration report is not a substitute for application smoke tests.
