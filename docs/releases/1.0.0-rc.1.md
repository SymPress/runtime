# Runtime 1.0.0-rc.1

This release candidate brings the frozen 1.x contract to Packagist. It includes
the beta 2 fix that allows Runtime to be installed before WordPress Core is added.
No new features are planned for the candidate cycle; fixes address regressions.

## Try the public package in an empty project

Use PHP 8.5+ and Composer 2.10.3+:

```sh
mkdir runtime-check
cd runtime-check
composer init --name=example/runtime-check --no-interaction
composer config allow-plugins.sympress/runtime true
composer require 'sympress/runtime:^1.0@RC'
vendor/bin/runtime --version
```

No custom repository or Runtime credentials are needed. Composer installs the
package and defers automatic setup while the project has neither WordPress Core
nor configuration. That is a package installation check, not a working WordPress
site. Follow [Getting started](../getting-started.md) to build a site.

## Upgrade an existing project

Preserve the working Composer lock, private environment artifacts and their
matching `var/runtime` payloads. Remove only the Runtime-specific VCS repository
from your root Composer manifest; keep WPackagist and any repositories required
by other dependencies. Allow candidate versions during evaluation:

```sh
composer require 'sympress/runtime:^1.0@RC' --no-plugins --no-scripts
composer install --no-interaction
vendor/bin/runtime validate
vendor/bin/runtime --no-interaction
vendor/bin/runtime doctor
```

Review and commit the lockfile: it pins the exact candidate version and source
revision; deploy it with `composer install`. The manifest constraint permits
later candidates and the stable 1.x release only during a deliberate update.
Review generated changes. Retain the existing download lock and
old deployment payloads. Preserve project URLs and web-server routes. From 0.1,
first follow the [0.2 upgrade notes](0.2.0.md); from 0.2, review the
[beta 1 API and bootstrap changes](1.0.0-beta.1.md).

Check homepage, login, admin, scheduled work and custom steps. Test `wp runtime`
only after reviewing the generated or manually registered WP-CLI bridge. Run
production diagnostics as the deployment's PHP identity where applicable.

## Candidate boundaries

The [compatibility policy](../compatibility-policy.md), [public API](../api.md)
and [platform table](../platforms.md) define the supported contract. Compatibility
adapters remain supported throughout 1.x and are deprecated for removal in 2.0.

The owner waived the two-week production and independent migration trials.
Automated recovery tests, consumer smoke checks and public installation tests do
not establish production field experience. Stable V1 still requires successful
candidate installation and consumer acceptance; this page does not certify those
checks before their results are recorded.
