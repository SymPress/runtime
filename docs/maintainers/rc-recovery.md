# Release-candidate recovery evidence

This records focused technical checks executed on 2026-09-30 against the current
V1 implementation worktree. It does not claim that an RC tag exists, that these
checks ran on a published RC artifact, or that a production rollout or observation
period has taken place. Repeat the release gates against the eventual tagged RC.

The two release-candidate tests were added because the existing individual
payload/environment tests did not exercise those full transition sequences.
Journal interruption and Composer replay reuse the existing meaningful fixtures
instead of duplicating them.

## Composer minimum and latest

The executed PHP runtime was 8.5.9. Both the Composer executable and installed
`composer/composer` library were 2.10.3. Live package metadata from
`composer show --all composer/composer --format=json` listed 2.10.3 as the newest
stable version on the evidence date, so the supported minimum and current latest
stable boundaries coincide. Development branches `2.10.x-dev` and `2.11.x-dev`
were not substituted for a stable release.

The two Composer tests above execute the real current boundary, including repeated
installation and recovery. They do **not** prove a transition between two distinct
Composer library versions: no newer stable version was available. The
[platform workflow](../../.github/workflows/platforms.yml) separately resolves the
minimum and current stable library and exercises real package relocation/proxies.
When the newest stable library becomes newer than the minimum, the release gate
must additionally replay an existing minimum-version consumer after upgrading to
that resolved version; record both exact versions and results here. Do not infer
cross-version upgrade evidence merely from two green matrix labels resolving the
same version.

## Commands and results

Executed in the existing PHP QA container, with repository-relative commands:

```sh
vendor/bin/phpunit --fail-on-skipped --fail-on-warning \
  tests/Integration/LayoutJournalCrashTest.php \
  tests/Integration/PackageLayoutTest.php \
  tests/Integration/RuntimeBundleTest.php \
  tests/Integration/EnvironmentTest.php \
  tests/Integration/ProductionEnvironmentTest.php \
  tests/Integration/ReleaseCandidateRecoveryTest.php
```

Result: **68 tests, 462 assertions; passed**, with no skips or warnings.

```sh
vendor/bin/phpunit --fail-on-skipped --fail-on-warning \
  --filter 'testFirstInstallRepeatInstallAndComposerCommandInIsolatedChild|testNoPluginsInstallAndStandaloneProduceTheSameFile' \
  tests/Integration/ComposerTest.php
vendor/bin/phpcs tests/Integration/ReleaseCandidateRecoveryTest.php
```

Results: **2 tests, 34 assertions; passed**, with no skips or warnings; coding
standards passed for the added test file. The two new scenarios alone passed
**2 tests, 82 assertions** and are already included in the 68-test batch.

All scenarios use independently created temporary projects and child PHP/Composer
processes. They do not access or reset a shared persistent database. The generated
configuration tests use a minimal WordPress hook/settings fixture: this demonstrates
configuration/payload/environment recovery, not a live production WordPress rollout.
The rollback fixture changes the supported bootstrap mode to generate a distinct
payload; it does not impersonate two published Runtime release versions.

Full package QA, real WordPress/database integration, consumer browser checks,
platform CI and release-artifact verification remain separate gates. The owner
waived the production/non-SymPress field trial and two-week observation period;
these technical fixtures do not create that missing operational experience.
